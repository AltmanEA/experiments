## Детерминированная управляющая плоскость

Поток управления Модератора, а также каждая Фаза, Консенсус и решение об Эскалации являются детерминированными функциями от проверенных выходов Роль. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария возвращается к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Машина состояний фазы

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| Откуда | Куда | Страж |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Манифест Сессии |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и целевой бюджет раунда не исчерпан |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранен; манифест обновлен в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом выводе Документатора (percheck failed). Precheck недоступен → override разрешен через council.override_precheck (precheck.overridden event). Override записан в манифест как pre_check_override; разрешает ровно один переход, после которого требуется еще один проход или новый override. |
| any | failed | Невосстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не редактирует состояние фазы напрямую; Резолюция поступает через интерфейс оператора. Хук обновления для быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Обработка статуса роли

`extract_role_status()` является единственным источником истины для Консенсус. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, сырой отзыв сохраняется, а Роль никогда не засчитывается как `agree`. Критический Вывод с некорректным обоснованием подчиняется тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Процесс проверки критического Вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы приводить к полному отклонению отзыва. Отсутствующая Роль ядра означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Проверка наличия Роль ядра выполняется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения Статус роли, но должен успешно завершиться перед любым продвижением протокола.
