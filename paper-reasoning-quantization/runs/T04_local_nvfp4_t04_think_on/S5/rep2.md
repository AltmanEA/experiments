## Deterministic Control Plane

Поток управления Модератора, а также каждая Фаза, Консенсус и решение об Эскалации являются детерминированными функциями проверенных выходов Роль. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может считывать произвольный текст исключительно для отображения; он никогда не интерпретирует его для принятия решений. При загрузке Сценария, если в манифесте Сессии не указан явный `scenario_id`, используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с учётом operator_approval согласно `service-contract/index.md` §Манифест Сессии |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-консенсус` с оставшимся бюджетом → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-эскалация`; ИЛИ `no-консенсус` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Precheck недоступен → переопределение разрешено через council.override_precheck (precheck.overridden event). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новое переопределение. |
| any | failed | Не восстанавливаемое IO или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления для быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для консенсуса. Извлечение с `invalid-format` является блокирующей ошибкой протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения, исходный отзыв сохраняется, а роль никогда не засчитывается как `согласие`. Критический вывод с некорректным обоснованием подчиняется тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Процесс проверки критического вывода): он понижается до `high` с сохранением исходного текста, а не приводит к полному отказу в рассмотрении отзыва. Отсутствие Роли ядра приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Присутствие Роли ядра проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения статуса роли, но должен успешно пройти перед любым продвижением протокола.
