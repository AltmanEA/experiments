## Deterministic Control Plane

Поток управления Модератора и решения по каждой Фазе, Консенсусу и Эскалации являются детерминированными функциями от выходных данных проверенных Ролей. Ни один LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке Сценария, если в манифесте Сессии не указан явный `scenario_id`, используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` отправка Задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка Консенсуса, `5` Резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно \`service-contract/index.md\` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет \`RoleStatus\` с \`extraction = parsed\` |
| 2 | awaiting-operator | Любое состояние \`invalid-format\` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых \`blocked-in-scope\` |
| 3 | 3 | Как минимум один \`blocked-in-scope\` и остался бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: \`Консенсус\` или \`conditional\` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: \`no-consensus\` с оставшимся бюджетом → возврат в Фаза 3; уменьшает \`no_consensus_budget\`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: \`blocked-Эскалация\`; ИЛИ \`no-consensus\` с исчерпанным бюджетом (\`no_consensus_budget\` достигает нуля → \`blocked-Эскалация\` с \`escalation_reason = information-gap\`) → \`awaiting-operator\` |
| 5 | resolved | Финальный Артефакт сохранен; манифест обновлен в последнюю очередь |
| awaiting-operator | \`resume_phase\` | Резолюция оператора привязана к \`escalation_id\` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Precheck недоступен → обход допускается через council.override_precheck (precheck.overridden event). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется еще одна проверка или новый обход. |
| any | failed | Ошибка IO, не подлежащая восстановлению, или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора для обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения, сырой отзыв сохраняется, а Роль никогда не учитывается как `Согласие`. Критический Вывод с недействительным обоснованием следует тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Critical Вывод Validation Process): он понижается до `high` с сохранением исходного текста, а не вызывает полный отказ в отзыве. Отсутствие Роль Core означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Роль Core проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения Статуса роли, но должен успешно пройти перед любым продвижением протокола.
