## Deterministic Control Plane

Поток управления модератора и каждый этап, консенсус и решение об эскалации являются детерминированными функциями проверенных выходов ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` разрешение, а также `awaiting-operator`, `resolved`, `failed`.

| От | До | Охрана |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены в соответствии с operator_approval согласно `service-contract/index.md` §Session Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице протокола-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокола-core §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице протокола-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Разрешение оператора привязано к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при обнаружении высокого/критического документа (не прошёл проверку). Если precheck недоступен → разрешено переопределение через council.override_precheck (событие precheck.overridden). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новое переопределение. |
| любой | failed | Невосстановимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; разрешение приходит через интерфейс оператора. Хук быстрого обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение с ошибкой `invalid-format` представляет собой блокирующую ошибку протокола: сессия переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения; сырой отзыв сохраняется, а роль никогда не учитывается как `agree`. Критическое замечание с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс валидации критических замечаний): оно понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению отзыва. Отсутствие роли Core вызывает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Ворота pre_check работают независимо от извлечения статуса роли, но должны успешно пройти перед любым продвижением протокола.
