## Deterministic Control Plane

Поток управления Модератора, а также решения по каждой фазе, консенсусу и эскалации являются детерминированными функциями валидированных выходов ролей. Ни одна LLM не участвует в управлении потоком или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке Сценария, если в манифесте Сессии не указан явный `scenario_id`, используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Условие |
|------|----|-------|
| 1 | 2 | Задача валидирована; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` со значением `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда или отсутствуют новые `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и сохранился бюджет целевых раундов |
| 4 | 5 | Согласно таблице §Outcome-to-Transition в protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition в protocol-core: `no-consensus` при оставшемся бюджете → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition в protocol-core: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция Оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (перепроверка не пройдена). При недоступности предпроверки → допускается отмена через council.override_precheck (событие precheck.overridden). Отмена записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новая отмена. |
| any | failed | Не восстанавливаемая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через поверхность оператора. Хук обновления для быстрого ревью `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение `invalid-format` является блокирующей ошибкой протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, формируемым структурно конвейером извлечения, исходный отзыв сохраняется, а Роль никогда не считается `Согласие`. Критический Вывод с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических Выводов): он понижается до `high` при сохранении исходного текста, вместо того чтобы приводить к прямому отклонению отзыва. Отсутствующая Роль Core вызывает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Проверка наличия Core-Роль выполняется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения Статуса роли, но должен быть успешно пройден перед любым продвижением протокола.
