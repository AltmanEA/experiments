## Deterministic Control Plane

Поток управления Модератора и каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями валидированных результатов работы ролей. Ни один LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария возвращается к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда или нет нового `blocked-in-scope` |
| 3 | 3 | Наличие хотя бы одного `blocked-in-scope` и сохранение бюджета целевого раунда |
| 4 | 5 | Согласно таблице протокола-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокола-core §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице протокола-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый сбой при высоком/критическом Выводе Документатора (перепроверка не пройдена). Недоступная предварительная проверка → разрешено переопределение через council.override_precheck (precheck.overridden event). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется новый проход или новое переопределение. |
| any | failed | Неустранимая ошибка IO или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого пересмотра и обновления `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение `invalid-format` является блокирующей ошибкой протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, структурно сгенерированным конвейером извлечения, необработанный отзыв сохраняется, а роль никогда не засчитывается как `agree`. Критический Вывод с некорректным обоснованием следует тому же принципу избегания отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критического Вывода): он понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению отзыва. Отсутствие Core Роль приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Core Роль проверяется на каждом пути, а не только перед упрощением. Шлюз `pre_check` функционирует независимо от извлечения статуса роли, но должен успешно пройти перед любым продвижением протокола.
