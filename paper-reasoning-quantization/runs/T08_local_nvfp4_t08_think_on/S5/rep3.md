## Deterministic Control Plane

Поток управления Модератора, а также каждая фаза, консенсус и решение об эскалации представляют собой детерминированные функции от валидированных выходов ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке Сценария происходит возврат к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` создание задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `ожидание оператора`, `разрешено`, `сбой`.

| От | До | Guard |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с одобрением оператора согласно `service-contract/index.md` §Манифест Сессии |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` со значением `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope`, и бюджет целевого раунда остаётся |
| 4 | 5 | Согласно таблице §Outcome-to-Transition в protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition в protocol-core: `no-consensus` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition в protocol-core: `blocked-Эскалация`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Предпроверка недоступна → переопределение разрешено через council.override_precheck (precheck.overridden event). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новое переопределение. |
| any | failed | Необратимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора обновления `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`` `extract_Роль_status()` `` — единственный источник истины для консенсуса. Извлечение с пометкой `invalid-format` является блокирующей ошибкой протокола: сессия переходит в `blocked-эскалация` с `Эскалация_reason = information-gap`, который структурно формируется конвейером извлечения; сырой отзыв сохраняется, и роль никогда не засчитывается как `Согласие`. Критический вывод с некорректным обоснованием следует тому же принципу нераспространения отказа (согласно `service-contract/error-management/index.md` §Процесс валидации критического вывода): он понижается до `high` с сохранением исходного текста, а не вызывает полный отказ от отзыва. Отсутствие Роль Core приводит к `blocked-эскалация` с `Эскалация_reason = risk-threshold-breach`. Присутствие Роль Core проверяется на каждом пути, а не только перед упрощением. Ворот `pre_check` функционирует независимо от извлечения статуса роли, но должен успешно пройти перед любым продвижением протокола.
