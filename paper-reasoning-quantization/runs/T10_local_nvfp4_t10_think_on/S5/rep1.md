## Deterministic Control Plane

Поток управления Модератора и каждое решение по Фазе, Консенсусу и Эскалации являются детерминированными функциями проверенных выводов Роли. Ни одна LLM не участвует в управлении потоком или проверке безопасности. Модератор может считывать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Если в манифесте Сессии не указан явный `scenario_id`, загрузка Сценария возвращается к `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| Откуда | Куда | Гард |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раундов, или отсутствует новый `blocked-in-scope` |
| 3 | 3 | Присутствует хотя бы один `blocked-in-scope` и остается бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-consensus` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-эскалация`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранен; manifest обновлен в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция Оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Вывод Документатора (percheck failed). Precheck недоступен → разрешено переопределение через council.override_precheck (precheck.overridden event). Переопределение записано в manifest как pre_check_override; разрешает ровно один переход, после чего требуется новый проход или новое переопределение. |
| any | failed | Неустранимая ошибка IO или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрой проверки зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с форматом `invalid-format` представляет собой блокирующую ошибку протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, который структурно формируется конвейером извлечения, исходный отзыв сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с недействительным обоснованием подчиняется тому же принципу избегания отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критического Вывода): он снижается до `high` с сохранением исходного текста, а не вызывает полное отклонение отзыва. Отсутствие Core-Роли приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Core-Роли проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения статуса Роли, но должен успешно завершиться перед любым продвижением протокола.
