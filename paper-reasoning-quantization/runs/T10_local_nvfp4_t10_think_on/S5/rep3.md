## Deterministic Control Plane

Поток управления Модератора, а также каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями от валидированных результатов ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария использует `default-council-session` (см. `scenario/default-council-session.yaml`) по умолчанию, если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` создание задачи, `2` индивидуальное ревью, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | Куда | Guard |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles проверены на соответствие operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или отсутствуют новые `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и целевой раунд бюджет остается |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-консенсус` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-эскалация`; ИЛИ `no-консенсус` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `причина_эскалации = information-gap`) → `awaiting-operator` |
| 5 | resolved | Конечный Артефакт сохранен; manifest обновлен в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатор (percheck failed). Precheck недоступен → override разрешено через council.override_precheck (precheck.overridden event). Override записывается в manifest как pre_check_override; разрешает ровно один переход, после чего требуется еще один проход или новый override. |
| any | failed | Невосстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` переходит к фазе. Оператор никогда не редактирует состояние фазы напрямую; Резолюция поступает через поверхность оператора. Хук обновления для быстрого обзора `SUBJ-007` зарезервирован, но не реализован в MVP-версии.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с пометкой `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в состояние `blocked-escalation` с параметром `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения; исходная проверка сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с некорректным обоснованием следует тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Critical Вывод Validation Process): он понижается до `high` с сохранением исходного текста, вместо того чтобы приводить к полному отклонению проверки. Отсутствие Роли Core трактуется как `blocked-escalation` с параметром `escalation_reason = risk-threshold-breach`. Наличие Роли Core проверяется на каждом пути, а не только перед упрощением. Ворота pre_check работают независимо от извлечения Статуса роли, но должны быть успешно пройдены перед любым переходом протокола на следующий этап.
