## Deterministic Control Plane

Поток управления Модератора, а также каждая Фаза, Консенсус и решение об Эскалации являются детерминированными функциями валидированных выходов Ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст исключительно для отображения; он никогда не интерпретирует его для принятия решений. При загрузке Сценария происходит возврат к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | К | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов или отсутствует новый `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-консенсус` с оставшимся бюджетом → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-эскалация`; ИЛИ `no-консенсус` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `причина_эскалации = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `id_эскалации` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый отказ при высоком/критическом выводе Документатор (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записывается в manifest как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| любой | failed | Не восстанавливается IO или нарушение протокола |

Только `orchestrator/` переводит в следующую фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого ревью обновления `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным достоверным источником для Консенсус. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, исходная проверка сохраняется, а Роль никогда не засчитывается как `agree`. Критический Вывод с некорректным обоснованием подчиняется тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Critical Вывод Validation Process): он понижается до `high` при сохранении исходного текста, вместо того чтобы приводить к полному отклонению проверки. Отсутствие Роль Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Проверка наличия Роль Core выполняется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения Статус роли, однако его успешное прохождение обязательно перед любым продвижением протокола.
