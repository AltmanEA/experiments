## Deterministic Control Plane

Модератор управляет потоком выполнения, и каждое решение, касающееся фазы, консенсуса и эскалации, является детерминированной функцией проверенных выходов ролей. Ни одна LLM не участвует в управлении потоком выполнения или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке сценария, если в манифесте сессии не указан явный `scenario_id`, происходит возврат к `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | До | Охранный блок |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены согласно operator_approval по `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | ожидающий-оператор | Любой статус `invalid-format` или отсутствует роль Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет для целевого раунда |
| 4 | 5 | Согласно таблице протокол-ядро §Результат-к-Переходу: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокол-ядро §Результат-к-Переходу: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | ожидающий-оператор | Согласно таблице протокол-ядро §Результат-к-Переходу: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён в последнюю очередь |
| ожидающий-оператор | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательный на границах фаз согласно определению слоя. Быстрый отказ при критическом или высоком Выводе Документатора (проверка не пройдена). Если precheck недоступен → разрешение через council.override_precheck (событие precheck.overridden). Переопределение фиксируется в манифесте как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новое переопределение. |
| любая | failed | Необратимая ошибка IO или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для **консенсуса**. **Эскалация** с `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, который формируется структурно конвейером извлечения, сырой обзор сохраняется, и **роль** никогда не считается в статусе **согласие**. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия отклонения (согласно разделу §Critical Вывод Validation Process файла `service-contract/error-management/index.md`): он понижается до уровня `high` с сохранением исходного текста, а не приводит к прямому отклонению обзора. Отсутствие **роли** Core вызывает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Выходной шлюз `pre_check` функционирует независимо от извлечения **статуса роли**, но должен успешно пройти перед любым продвижением протокола.
