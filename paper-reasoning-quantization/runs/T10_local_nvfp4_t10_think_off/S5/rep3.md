## Deterministic Control Plane

Поток управления Модератора, а также каждая фаза, консенсус и решение об эскалации являются детерминированными функциями валидированных выходов ролей. Никакая LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указана явная `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание-оператора`, `разрешено`, `неудача`.

| От | Кому | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope`, и остаётся бюджет целевых раундов |
| 4 | 5 | Согласно таблице протокольного ядра §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокольного ядра §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице протокольного ядра §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Окончательный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Разрешение оператора связано с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высокой/критической Выводе Документатора (percheck не прошёл). Недоступность precheck → разрешение на оверрайд через council.override_precheck (событие precheck.overridden). Оверрайд записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый оверрайд. |
| any | failed | Невоcстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` продвигает **фазу**. Оператор никогда не редактирует состояние **фазы** напрямую; **резолюция** поступает через интерфейс оператора. Хук улучшения `SUBJ-007` для быстрой проверки зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для **консенсуса**. Извлечение с `invalid-format` является блокирующей ошибкой протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения; сырой обзор сохраняется, а **роль** никогда не считается как `agree`. Критический **вывод** с невалидным обоснованием подчиняется тому же принципу непризнания (согласно `service-contract/error-management/index.md` §Процесс валидации критических выводов): он понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению обзора. Отсутствие роли Core — это `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Шлюз `pre_check` работает независимо от извлечения **статуса роли**, но должен пройти успешно перед любым продвижением протокола.
