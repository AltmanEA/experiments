## Deterministic Control Plane

Поток управления модератором и каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями проверенных выходов ролей. Никакая LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария переходит к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача Задачи, `2` индивидуальный ревью, `3` обсуждение, `4` проверка Консенсуса, `5` Резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | Кому | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | ожидание-оператора | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достижение предела раундов, или отсутствие новых `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице перехода исхода в протоколе-ядре: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице перехода исхода в протоколе-ядре: `no-consensus` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | ожидание-оператора | Согласно таблице перехода исхода в протоколе-ядре: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `ожидающий-оператора` |
| 5 | resolved | Окончательный артефакт сохранён; манифест обновлён в последнюю очередь |
| ожидание-оператора | `resume_phase` | Резолюция оператора связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при обнаружении высокого/критического Документатором вывода (не пройдена precheck). Доступность precheck недоступна → разрешение обхода через council.override_precheck (событие precheck.overridden). Обход фиксируется в манифесте как pre_check_override; разрешает ровно один переход, после чего требуется другой проход или новое разрешение. |
| любой | failed | Не восстанавливаемое IO-нарушение или нарушение протокола |

Только `orchestrator/` продвигает **фазу**. Оператор никогда не редактирует состояние фазы напрямую; **резолюция** приходит через интерфейс оператора. Хук обновления быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение с `invalid-format` является блокирующей ошибкой протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения; сырой рецензированный материал сохраняется, а роль никогда не считается `agree`. Критический вывод с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению рецензии. Отсутствие роли Core вызывает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Ворота pre_check работают независимо от извлечения статуса роли, но должны успешно пройти прежде, чем будет осуществлено любое продвижение протокола.
