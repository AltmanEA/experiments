## Deterministic Control Plane

Поток управления Модератора, а также решения по каждой фазе, консенсусу и эскалации являются детерминированными функциями валидированных выходных данных ролей. Никакая LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке сценария, если в манифесте сессии не указан явный `scenario_id`, используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный ревью, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда или отсутствие новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и сохранился целевой бюджет раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-Консенсус` при наличии остатка бюджета → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-Эскалация`; ИЛИ `no-Консенсус` при исчерпании бюджета (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `Эскалация_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранен; манифест обновлен в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция Оператора привязана к `Эскалация_id` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый сбой при высоком/критическом Выводе Документатора (не прошел percheck). Предварительная проверка недоступна → разрешение на отмену через council.override_precheck (событие precheck.overridden). Отмена записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется повторная проверка или новая отмена. |
| any | failed | Неисправимая ошибка IO или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, сырой обзор сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с недействительным обоснованием подчиняется тому же принципу непринятия отклонения (согласно `service-contract/error-management/index.md` §Critical Вывод Validation Process): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать прямое отклонение обзора. Отсутствие Роль Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Роль Core проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения Статус роли, но должен успешно пройти перед любым переходом протокола.
