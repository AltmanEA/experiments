## Deterministic Control Plane

Поток управления Модератора, а также каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями проверенных выходов ролей. Ни одна LLM не участвует в управлении потоком или проверке безопасности. Модератор может считывать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Если в манифесте сессии не указан явный `scenario_id`, при загрузке Сценария используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` отправка Задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка Консенсуса, `5` Резолюция, а также `ожидание оператора`, `выполнено`, `сбой`.

| От | До | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` со значением `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раундов или отсутствуют новые `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет для целевого раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition в protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition в protocol-core: `no-consensus` при наличии бюджета → возврат к Фазе 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition в protocol-core: `blocked-эскалация`; ИЛИ `no-consensus` при исчерпании бюджета (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Окончательный артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаза согласно определению слоя. Немедленный сбой при высоком/критическом выводе Документатора (сбой percheck). Недоступность precheck → допускается override через council.override_precheck (событие precheck.overridden). Override записывается в манифест как pre_check_override; позволяет ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Невосстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` продвигает Фазу. Оператор никогда не редактирует состояние Фазы напрямую; Резолюция поступает через интерфейс оператора. Хук быстрого пересмотра обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, сырой отзыв сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Critical Вывод Validation Process): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать прямой отказ в отзыве. Отсутствующая базовая Роль означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие базовой Роль проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения Статуса роли, но должен завершиться успешно перед любым продвижением протокола.
