## Deterministic Control Plane

Поток управления Модератора и каждая Фаза, Консенсус и решение об Эскалации являются детерминированными функциями проверенных выходных данных Ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария использует `default-council-session` по умолчанию (см. `scenario/default-council-session.yaml`), когда в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Ограничение |
|------|----|-------|
| 1 | 2 | Задача валидирована; Сценарий загружен; locked_roles разрешены в соответствии с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Хотя бы один `blocked-in-scope` и остаётся целевой бюджет раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition protocol-core: `no-consensus` при оставшемся бюджете → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition protocol-core: `blocked-Эскалация`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция Оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Прерывается немедленно при высоком/критическом Выводе Документатора (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый override. |
| any | failed | Невосстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` переходит к следующей фазе. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через поверхность оператора. Хук обновления для быстрого ревью `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсус. Извлечение с `invalid-format` является блокирующей ошибкой протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, необработанный обзор сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с недействительным обоснованием следует тому же принципу отсутствия отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критических Выводов): оно понижается до `high` с сохранением исходного текста, вместо прямого отклонения обзора. Отсутствие Роль Core означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Присутствие Роль Core проверяется на каждом пути, а не только перед упрощением. Ворота pre_check функционируют независимо от извлечения Статус роли, но должны успешно пройти перед любым продвижением протокола.
