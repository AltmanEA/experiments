## Deterministic Control Plane

Поток управления Модератора и каждое решение по Фазе, Консенсусу и Эскалации являются детерминированными функциями валидированных выходов Роль. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария возвращается к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` персональная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | К | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раундов или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остался бюджет целевого раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition в protocol-core: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition в protocol-core: `no-Консенсус` при оставшемся бюджете → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition в protocol-core: `blocked-Эскалация`; ИЛИ `no-Консенсус` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый отказ при высоком/критическом Вывод Документатор (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записан в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Неисправимая ошибка IO или нарушение протокола |

Только `orchestrator/` переходит к следующей фазе. Оператор никогда не изменяет состояние фазы напрямую; Резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, формируемым конвейером извлечения, сырой отзыв сохраняется, а Роль никогда не засчитывается как `Согласие`. Критический Вывод с некорректным обоснованием подчиняется тому же принципу отсутствия отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критического Вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать прямой отказ в рассмотрении. Отсутствие Роль Core трактуется как `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Проверка наличия Роль Core выполняется на каждом пути, а не только перед упрощением. Ворота pre_check функционируют независимо от извлечения Статус роли, но должны успешно пройти перед любым продвижением протокола.
