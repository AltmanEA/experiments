## `pre_check` Gate

### Scope and Enforcement Point

Шлюз `pre_check` представляет собой проверку целостности артефактов документации перед тем, как будут зафиксированы переходы состояния протокола. Он выполняется в слое 2 (поверхность оператора) в виде синхронного вызова метода `audit(pre_check=true)` у Документатора и возвращает решение вызывающей стороне в рамках того же вызова.

- **Охват цели:** все манифест-документы, относящиеся к текущей сессии (определяются по `target_id` из активного сценария).
- **Точка принудительного применения:** вызывается на каждом переходе между фазами (`2 → 3`, `3 → 4`, `4 → 5`) перед фиксацией нового состояния фазы в Слое 1.
- **Переходы с контролем:** `2 → 3` (начало обсуждения), `3 → 4` (проверка консенсуса), `4 → 5` (резолюция). Переход разрешён только при вердикте `pass`.
- **Передача вердикта в Слой 1:** поверхность записывает результат вердикта (pass/fail/причина) в поле манифеста `pre_check_override` при переопределении или генерирует событие `precheck.failed`; среда выполнения считывает это поле/событие на следующей оценке границы и либо продолжает выполнение, либо блокирует его соответственно.

### Verdict Logic

| Условие | Вердикт | Действие |
|---------|---------|----------|
| Для целевой области нет выводов с уровнем `high`/`critical` | `pass` | Продолжить переход |
| Присутствует любой вывод с уровнем `high` или `critical` | `fail` | Заблокировать переход; сгенерировать событие `precheck.failed` |
| Документатор недоступен (ошибка сети, таймаут, сервис недоступен) | `unavailable` | Заблокировать переход; сгенерировать событие `precheck.unavailable` (см. Режим Override ниже) |
| Реестр аудитов Документатора отсутствует/поврежден/не читается | `fail` | Заблокировать переход (fail-closed согласно C-03) |

### Documenter Unavailable — Override Mode

Когда Документатор недоступен (вердикт `unavailable`), Модератор MVP НЕ ДОЛЖНБ блокировать бесконечно. Аутентифицированный вызов `council.override_precheck(reason, operator_id)` может быть выполнен даже в случае неудачи:

- Запись о принудительном обходе содержит `reason` (свободный текст, объясняющий, почему контрольная точка была обойдена).
- Информация о принудительном обходе записывается в манифест через поле `pre_check_override`.
- Событие `precheck.overridden` синхронно генерируется в момент вызова механизма принудительного обхода.
- Принудительный обход разрешает ровно один последующий переход фазы без нового аудита. После этого перехода для следующей контрольной точки требуется повторная проверка или новый принудительный обход.
- Принудительный обход никогда не позволяет обойти требования присутствия роли Core, правила консенсуса или механизмы обеспечения целостности эскалации.
