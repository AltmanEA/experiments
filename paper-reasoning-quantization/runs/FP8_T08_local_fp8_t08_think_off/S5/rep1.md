## Deterministic Control Plane

Поток управления Модератора и каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями проверенных выходов Роль. Ни один LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария по умолчанию переходит к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание оператора`, `разрешено`, `не удалось`.

| От | До | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены в соответствии с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | ожидание-оператора | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице Outcome-to-Transition §protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице Outcome-to-Transition §protocol-core: `no-consensus` с оставшимся бюджетом → возврат в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | ожидание-оператора | Согласно таблице Outcome-to-Transition §protocol-core: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `ожидание-оператора` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён в последнюю очередь |
| ожидание-оператора | `resume_phase` | Резолюция оператора связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при обнаружении важного/критического вывода Документатора (перечек не прошёл). Если precheck недоступен → разрешение через council.override_precheck (событие precheck.overridden). Разрешение записывается в манифест как pre_check_override; позволяет ровно один переход, после чего требуется ещё одна проверка или новое разрешение. |
| любой | failed | Неисправимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрой проверки зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для **консенсуса**. Извлечение с `invalid-format` является блокирующей ошибкой протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения; сырой обзор сохраняется, и **роль** никогда не считается `agree`. Критическое **вывод** с недействительным обоснованием следует тому же принципу отказа от отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критического вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать прямое отклонение обзора. Отсутствующая Core **роль** приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Core-**роли** проверяется на каждом пути, а не только перед упрощением. Врата pre_check работают независимо от извлечения **статуса роли**, но должны быть успешными перед любым продвижением протокола.
