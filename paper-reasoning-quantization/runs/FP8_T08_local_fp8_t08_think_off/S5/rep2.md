## Deterministic Control Plane

Поток управления Модератора, а также каждый этап, процесс достижения консенсуса и решения об эскалации являются детерминированными функциями валидированных выходных данных Ролей. Ни одна LLM не участвует в управлении потоком или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание оператора`, `разрешено`, `не удалось`.

| От | До | Страж |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены согласно operator_approval в `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая Core роль |
| 3 | 4 | Достигнут лимит раундов или нет новых `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-consensus` при наличии бюджета → возврат в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Итоговый артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при критическом Выводе Документатора (проверка не пройдена). Недоступность предварительной проверки → разрешено переопределение через council.override_precheck (событие precheck.overridden). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется новый проход или новое переопределение. |
| any | failed | Невосстановимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не изменяет состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для **консенсуса**. Извлечение с форматом `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения; сырой отзыв сохраняется, а **роль** никогда не учитывается как `agree`. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отказ от отзыва. Отсутствие **роли** Core приводит к состоянию `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие **роли** Core проверяется на каждом пути, а не только перед упрощением. Врата `pre_check` функционируют независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.
