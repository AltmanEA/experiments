## Deterministic Control Plane

Поток управления Модератора, а также каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями от валидированных выходов Роли. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание оператора`, `разрешено`, `не удалось`.

| От | До | Охранник |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие Core роли |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition протокол-ядро: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition протокол-ядро: `no-consensus` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition протокол-ядро: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Резолюция оператора связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (проверка не пройдена). Если предварительная проверка недоступна → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новое разрешение. |
| any | failed | Не восстанавливаемая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для **консенсуса**. Извлечение с `invalid-format` является блокирующей ошибкой протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения; сырой обзор сохраняется, а **роль** никогда не учитывается как `agree`. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению обзора. Отсутствие **роли** Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Ворота `pre_check` работают независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.
