## Deterministic Control Plane

Поток управления Модератора, а также каждая фаза, консенсус и решение об эскалации являются детерминированными функциями от валидированных выходов Роли. LLM не участвует в управлении потоком или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария использует значение по умолчанию `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | До | Охранный переход |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | ожидание-оператора | Любой статус `invalid-format` или отсутствие Core роли |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы одна `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице протокол-ядро §Результат-в-Переход: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокол-ядро §Результат-в-Переход: `no-consensus` с оставшимся бюджетом → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | ожидание-оператора | Согласно таблице протокол-ядро §Результат-в-Переход: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `ожидание-оператора` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| ожидание-оператора | `resume_phase` | Резолюция оператора связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при критическом/высоком выводе Документатора (перепроверка не пройдена). Недоступность предварительной проверки → разрешение переопределения через council.override_precheck (событие precheck.overridden). Переопределение записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё одна проверка или новое переопределение. |
| любой | failed | Не восстанавливаемая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для **консенсуса**. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения, необработанный отзыв сохраняется, и **роль** никогда не считается **согласием**. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отклонение отзыва. Отсутствующая роль Core является `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Врата pre_check работают независимо от извлечения **статуса роли**, но должны быть успешными перед любым продвижением протокола.
