## Deterministic Control Plane

Модератор контролирует поток выполнения, и каждая фаза, консенсус и решение об эскалации являются детерминированными функциями от проверенных выходов ролей. Ни одна LLM не участвует в управлении потоком выполнения или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария использует значение `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | До | Охранник |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены в соответствии с операторским одобрением согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие Core роли |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | По крайней мере один `blocked-in-scope` и остаётся целевой бюджет раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition протокольного ядра: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition протокольного ядра: `no-consensus` с оставшимся бюджетом → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition протокольного ядра: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Операторская резолюция связана с `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом выводе Документатора (проверка не пройдена). Недоступность precheck → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый обход. |
| любой | failed | Невосстановимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает **фазу**. Оператор никогда не изменяет состояние **фазы** напрямую; **резолюция** поступает через интерфейс оператора. Хук обновления быстрого обзора `SUBJ-007` зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для **консенсуса**. Извлечение с `invalid-format` является блокирующей ошибкой протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, сырой обзор сохраняется, а **роль** никогда не засчитывается как **согласие**. Критический **вывод** с недействительным обоснованием следует тому же принципу непризнания (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не приводит к полному отклонению обзора. Отсутствие **роли** ядра приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие **роли** ядра проверяется на каждом пути, а не только перед упрощением. Ворота `pre_check` работают независимо от извлечения **статуса роли**, но должны быть успешными перед любым продвижением протокола.
