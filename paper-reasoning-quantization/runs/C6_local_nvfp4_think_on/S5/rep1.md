## Deterministic Control Plane

Поток управления Модератора и решения по каждой фазе, консенсусу и эскалации являются детерминированными функциями от валидированных выходов ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. При загрузке сценария, если в манифесте сессии не указан явный `scenario_id`, используется `default-council-session` (см. `scenario/default-council-session.yaml`).

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| Откуда | Куда | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-consensus` с оставшимся бюджетом → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; manifest обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Вывод Документатор (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записан в manifest как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Невосстанавливаемая ошибка IO или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления для быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсус. Извлечение с `invalid-format` — это блокирующая ошибка протокола: сессия переходит в `blocked-эскалацию` с `reason_эскалации = information-gap`, сформированным структурно конвейером извлечения; сырой отзыв сохраняется, а роль никогда не учитывается как `согласие`. Критический вывод с недействительным обоснованием следует тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отказ от проверки. Отсутствие Роль Core приводит к `blocked-эскалации` с `reason_эскалации = risk-threshold-breach`. Проверка наличия Роль Core выполняется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения Статус роли, но должен успешно завершиться перед любым продвижением протокола.
