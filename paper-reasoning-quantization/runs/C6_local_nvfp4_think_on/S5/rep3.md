## Deterministic Control Plane

Поток управления Модератора и решения по каждой фазе, консенсусу и эскалации являются детерминированными функциями от валидированных выходов ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария использует `default-council-session` (см. `scenario/default-council-session.yaml`) по умолчанию, когда явный `scenario_id` не указан в манифесте сессии.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | К | Условие |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице protocol-core §Outcome-to-Transition: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице protocol-core §Outcome-to-Transition: `no-Консенсус` при наличии бюджета → повторный вход в Фаза 3; уменьшает `no_Консенсус_budget`. |
| 4 | awaiting-operator | Согласно таблице protocol-core §Outcome-to-Transition: `blocked-Эскалация`; ИЛИ `no-Консенсус` при исчерпании бюджета (`no_Консенсус_budget` достигает нуля → `blocked-Эскалация` с `Эскалация_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `Эскалация_id` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый отказ при высоком/критическом Вывод Документатор (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записан в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Не восстанавливаемая IO-ошибка или нарушение протокола |

Только `orchestrator/` переводит в следующую фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение с форматом `invalid-format` является блокирующей ошибкой протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, формируемым структурно конвейером извлечения; сырой отзыв сохраняется, а роль никогда не засчитывается как `Согласие`. Критический вывод с некорректным обоснованием следует тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Процесс проверки критического вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы приводить к полному отклонению отзыва. Отсутствующая Роль Core означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Роль Core проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check работает независимо от извлечения Статуса роли, но должен успешно пройти перед любым продвижением протокола.
