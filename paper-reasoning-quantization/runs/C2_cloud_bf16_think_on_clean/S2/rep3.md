## Escalation Protocol


Эскалация — это механизм, который срабатывает, когда внутренние средства группы агентов исчерпаны. Он позволяет системе признать собственные ограничения и передать проблему человеческому оператору.

### Escalation Reasons

Система направляет задачу оператору по одной из следующих трех причин.

**Информационный пробел.** Агенты готовы приступить к выполнению задачи, но им не хватает входных данных, необходимых для принятия обоснованного решения. Агентам запрещено строить допущения исключительно ради завершения процесса — требуется точное изложение фактов. Типичный пример: роль безопасности запрашивает сведения о том, как хранятся конфиденциальные данные, но пользователь не указал это в задаче. В подобных ситуациях оператор получает конкретный запрос с перечислением недостающей информации.

**Неразрешимый конфликт.** Две или более роли занимают принципиально разные позиции по вопросу, и обсуждение не приводит к согласию. Например, архитектор предлагает подключить два компонента напрямую для повышения производительности, тогда как специалист по безопасности категорически запрещает это из-за угрозы несанкционированного доступа. Обе стороны аргументированы, и ни одна не готова уступить. Оператор получает сводку обеих позиций и просится принять окончательное решение.

### Escalation Document

 - Combine & Refine: Он включает тип эскалации, название роли, которая её инициировала, уровень серьёзности (средний, высокий, критический), описание блокирующей проблемы, позиции участников (в случае конфликта), конкретный запрос к оператору, а также, при необходимости, запасной план действий на случай отсутствия ответа в течение заданного временного окна.


 - Эскалация -> Эскалация (used as эскалации/эскалацию, which is grammatically correct)


Каждый запрос оператору сопровождается структурированной записью. Она включает тип эскалации, название роли, которая инициировала эскалацию, уровень серьёзности (средний, высокий, критический), описание блокирующей проблемы, позиции участников (в случае конфликта), конкретный запрос к оператору, а также, при необходимости, резервный план действий на случай отсутствия ответа в течение заданного временного окна.

### Escalation Resolution Paths

Существует три возможных исхода эскалации:


- **Вмешательство оператора.** Человек предоставляет недостающую информацию или принимает решение по итогам конфликта сторон. Как только ответ получен, работа продолжается.


- **Отложенный фоллбэк.** Если в отведенное время не поступает ответа, применяется заранее определённая стратегия по решению проекта. Runtime автоматически обеспечивает это: при возобновлении сессии, если `timeout_at` истёк, применяется `fallback_strategy` из `EscalationRecord` без дополнительного ввода со стороны оператора.
- **Частичное продолжение.** Части задачи, не заблокированные эскалацией, выполняются; оставшаяся информация переносится в следующий цикл обработки.
