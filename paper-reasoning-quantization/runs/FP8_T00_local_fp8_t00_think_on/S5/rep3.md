## Deterministic Control Plane

Поток управления Модератора и каждое решение по Фазе, Консенсусу и Эскалации являются детерминированными функциями от валидированных выходов Роли. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может считывать свободный текст исключительно для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария откатывается к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| Откуда | Куда | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles сопоставлены с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остался бюджет целевого раунда |
| 4 | 5 | Согласно таблице §Outcome-to-Transition в protocol-core: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition в protocol-core: `no-консенсус` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition в protocol-core: `blocked-эскалация`; ИЛИ `no-консенсус` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-эскалация` с `reason_эскалации = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `id_эскалации` |
| N → N+1 | Обязательно на границах Фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записан в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Невосстанавливаемая ошибка IO или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора для обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для Консенсуса. Извлечение с `invalid-format` является блокирующей ошибкой протокола: Сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения, сырой обзор сохраняется, а Роль никогда не засчитывается как `согласие`. Критический Вывод с некорректным обоснованием следует тому же принципу сохранения без отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать полный отказ от обзора. Отсутствие Роль Core означает `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Проверка наличия Роль Core выполняется на каждом пути, а не только перед упрощением. Шлюз `pre_check` функционирует независимо от извлечения Статуса роли, но его успешное прохождение обязательно перед любым продвижением протокола.
