## Deterministic Control Plane

Поток управления Модератора, а также каждая Фаза, Консенсус и решение об Эскалации являются детерминированными функциями проверенных выходов Ролей. Ни одна LLM не участвует в управлении потоком или проверке безопасности. Модератор может считывать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария переходит к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальная проверка, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | К | Охрана |
|------|----|-------|
| 1 | 2 | Задача проверена; Сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствующая роль Core |
| 3 | 4 | Достигнут лимит раунда или нет новых `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и остался бюджет целевого раунда |
| 4 | 5 | Согласно protocol-core §Outcome-to-Transition table: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно protocol-core §Outcome-to-Transition table: `no-consensus` с оставшимся бюджетом → возврат в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно protocol-core §Outcome-to-Transition table: `blocked-Эскалация`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `Эскалация_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `Эскалация_id` |
| N → N+1 | Обязательно на границах Фаза согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Precheck недоступен → override разрешён через council.override_precheck (precheck.overridden event). Override записан в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый override. |
| any | failed | Невосстановимая ошибка IO или нарушение протокола |

Только `orchestrator/` переходит к следующей фазе. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук быстрого обзора обновления `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, исходный отзыв сохраняется, а роль никогда не засчитывается как `согласие`. Критический вывод с некорректным обоснованием подчиняется тому же принципу отсутствия отклонения (согласно `service-contract/error-management/index.md` §Процесс проверки критического вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы приводить к полному отклонению отзыва. Отсутствие Роль Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие Роль Core проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения статуса роли, но должен успешно завершиться перед любым переходом протокола.
