## Deterministic Control Plane

Поток управления Модератора и каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями от валидированных выходов Роли. Никакая LLM не участвует в потоке управления или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария использует значение по умолчанию `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| От | До | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице протокола-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокола-core §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице протокола-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при критическом/высоком выводе Документатора (не прошёл precheck). Если precheck недоступен → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый обход. |
| any | failed | Не восстанавливаемая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для **консенсуса**. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения; сырой обзор сохраняется, и **роль** никогда не учитывается как `agree`. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс валидации критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отказ от обзора. Отсутствие **роли** Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Ворота `pre_check` работают независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.
