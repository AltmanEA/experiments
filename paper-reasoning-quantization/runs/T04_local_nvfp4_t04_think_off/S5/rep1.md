## Deterministic Control Plane

Управление потоком выполнения Модератора, а также каждое решение по фазе, консенсусу и эскалации являются детерминированными функциями от валидированных выходов Роли. Ни одна LLM не участвует в управлении потоком выполнения или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария переходит к `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` подача задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание-оператора`, `разрешено`, `неудачно`.

| От | К | Ограничение |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | ожидание-оператора | Любой статус `invalid-format` или отсутствие Core роли |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице протокол-ядро §Результат-в-Переход: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокол-ядро §Результат-в-Переход: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фазу 3; уменьшает `no_consensus_budget`. |
| 4 | ожидание-оператора | Согласно таблице протокол-ядро §Результат-в-Переход: `blocked-escalation`; ИЛИ `no-consensus` при исчерпании бюджета (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `ожидание-оператора` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| ожидание-оператора | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высокой/критической Вывод Документатора (percheck не прошёл). Если precheck недоступен → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый обход. |
| любой | failed | Невосстановимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через поверхность оператора. Хук обновления `SUBJ-007` быстрого обзора зарезервирован, но не реализован в MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для **консенсуса**. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сформированным структурно конвейером извлечения, сырой обзор сохраняется, а **роль** никогда не учитывается как **согласие**. Критический **вывод** с недействительным обоснованием подчиняется тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отклонение обзора. Отсутствие **роли** Core приводит к состоянию `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие **роли** Core проверяется на каждом пути, а не только перед упрощением. Ворота pre_check работают независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.
