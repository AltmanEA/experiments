## Deterministic Control Plane

Поток управления Модератора и решения для каждой Фазы, Консенсуса и Эскалации являются детерминированными функциями от валидированных выходов Ролей. Ни одна LLM не участвует в потоке управления или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка Сценария использует `default-council-session` (см. `scenario/default-council-session.yaml`) по умолчанию, когда в манифесте Сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, плюс `awaiting-operator`, `resolved`, `failed`.

| От | Куда | Страж |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | У каждой активной роли есть `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Наличие любого статуса `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раунда, или отсутствуют новые `blocked-in-scope` |
| 3 | 3 | Как минимум один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно protocol-core §Outcome-to-Transition table: `Консенсус` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно protocol-core §Outcome-to-Transition table: `no-consensus` с оставшимся бюджетом → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно protocol-core §Outcome-to-Transition table: `blocked-Эскалация`; ИЛИ `no-consensus` с исчерпанным бюджетом (`no_consensus_budget` достигает нуля → `blocked-Эскалация` с `Эскалация_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Итоговый Артефакт сохранён; манифест обновлён в последнюю очередь |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (percheck failed). Предварительная проверка недоступна → обход разрешён через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после которого требуется ещё один проход или новый обход. |
| any | failed | Невосстановимый ввод-вывод или нарушение протокола |

Только `orchestrator/` переводит фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через поверхность оператора. Хук обновления для быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` является единственным источником истины для консенсуса. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: сессия переходит в `blocked-эскалацию` с `причина_эскалации = information-gap`, сгенерированной структурно конвейером извлечения, сырой отзыв сохраняется, а роль никогда не засчитывается как `согласие`. Критический вывод с некорректным обоснованием подчиняется тому же принципу непринятия отказа (согласно `service-contract/error-management/index.md` §Процесс проверки критического вывода): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать полный отказ в отзыве. Отсутствие роли Core является `blocked-эскалацией` с `причина_эскалации = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Шлюз pre_check функционирует независимо от извлечения статуса роли, но должен быть успешно выполнен перед любым продвижением протокола.
