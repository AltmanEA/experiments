## Deterministic Control Plane

Управление потоком выполнения Модератора, а также каждая фаза, консенсус и решение об эскалации являются детерминированными функциями проверенных выходов ролей. Ни одна LLM не участвует в управлении потоком выполнения или проверке безопасности. Модератор может читать свободный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Phase State Machine

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `ожидание оператора`, `разрешено`, `не выполнено`.

| От | До | Охрана |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles согласованы с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие роли Core |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице Outcome-to-Transition в protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице Outcome-to-Transition в protocol-core: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице Outcome-to-Transition в protocol-core: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Резолюция оператора привязана к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом Выводе Документатора (проверка не пройдена). Если precheck недоступен → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новый обход. |
| any | failed | Неисправимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Role Status Handling

`extract_role_status()` — единственный источник истины для **консенсуса**. Извлечение с `invalid-format` является блокирующей ошибкой протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения; сырой обзор сохраняется, а **роль** никогда не учитывается как `agree`. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, вместо того чтобы вызывать полный отказ от обзора. Отсутствие **роли** Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие **роли** Core проверяется на каждом пути, а не только перед упрощением. Врата `pre_check` работают независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.
