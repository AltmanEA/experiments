# Карточка X22 — прогон из фикстуры S7 (повтор 1)

Строки пронумерованы (`N| текст`); в вопросах ссылки — на эти номера.

## EN-источник

```
  1| ## `pre_check` Gate
  2| 
  3| ### Scope and Enforcement Point
  4| 
  5| The `pre_check` gate is an integrity check on documentation artifacts before protocol state transitions are committed. It runs in Layer 2 (operator surface) as a synchronous call to Documenter's `audit(pre_check=true)` and returns a verdict to the caller within the same invocation.
  6| 
  7| - **Target scope:** all manifest documents relevant to the current session (identified by `target_id` from the active scenario).
  8| - **Enforcement point:** invoked at every phase boundary transition (`2 → 3`, `3 → 4`, `4 → 5`) before committing the new phase state in Layer 1.
  9| - **Gated transitions:** `2 → 3` (discussion start), `3 → 4` (consensus check), `4 → 5` (resolution). Transition is permitted only when the verdict is `pass`.
 10| - **Verdict handoff to Layer 1:** the surface writes the verdict result (pass/fail/reason) into the manifest field `pre_check_override` on override or emits a `precheck.failed` event; the runtime reads this field/event at the next boundary evaluation and either proceeds or blocks accordingly.
 11| 
 12| ### Verdict Logic
 13| 
 14| | Condition | Verdict | Action |
 15| |-----------|---------|--------|
 16| | No `high`/`critical` findings for target scope | `pass` | Proceed with transition |
 17| | Any `high` or `critical` finding present | `fail` | Block transition; emit `precheck.failed` event |
 18| | Documenter is unavailable (network error, timeout, service down) | `unavailable` | Block transition; emit `precheck.unavailable` event (see Override mode below) |
 19| | Documenter audit registry is absent/corrupted/unreadable | `fail` | Block transition (fail-closed per C-03) |
 20| 
 21| ### Documenter Unavailable — Override Mode
 22| 
 23| When Documenter cannot be reached (`unavailable` verdict), the moderator MVP MUST NOT block indefinitely. An authenticated `council.override_precheck(reason, operator_id)` may proceed despite the failure:
 24| 
 25| - The override records `reason` (free text explaining why the gate was bypassed).
 26| - The override is written to the manifest via the `pre_check_override` field.
 27| - A `precheck.overridden` event is emitted synchronously during the override invocation.
 28| - The override permits exactly one subsequent phase transition without a fresh audit. After that transition, the next boundary requires another pass or a new override.
 29| - An override never bypasses Core-role presence, consensus rules, or escalation integrity gates.
```

## RU-вывод

```
  1| ## `pre_check` Gate
  2| 
  3| ### Scope and Enforcement Point
  4| 
  5| Шлюз `pre_check` представляет собой проверку целостности артефактов документации перед фиксацией переходов состояния протокола. Он выполняется на уровне 2 (на уровне оператора) в виде синхронного вызова метода `audit(pre_check=true)` у Документатора и возвращает вердикт вызывающей стороне в рамках того же вызова.
  6| 
  7| - **Целевой охват:** все манифест-документы, относящиеся к текущей сессии (определяемые `target_id` из активной сценарии).
  8| - **Точка принудительного выполнения:** вызывается на каждом переходе между фазами (`2 → 3`, `3 → 4`, `4 → 5`) перед фиксацией нового состояния фазы в Слое 1.
  9| - **Ограниченные переходы:** `2 → 3` (начало обсуждения), `3 → 4` (проверка консенсуса), `4 → 5` (резолюция). Переход разрешен только при вердикте `pass`.
 10| - **Передача вердикта в Слой 1:** поверхность записывает результат вердикта (pass/fail/причина) в поле манифеста `pre_check_override` при переопределении или генерирует событие `precheck.failed`; среда выполнения считывает это поле/событие на следующей оценке границы и либо продолжает выполнение, либо блокирует его.
 11| 
 12| ### Verdict Logic
 13| 
 14| | Условие | Вердикт | Действие |
 15| |-----------|---------|--------|
 16| | Нет `high`/`critical` выводов для целевой области | `pass` | Продолжить переход |
 17| | Есть любой `high` или `critical` вывод | `fail` | Блокировать переход; сгенерировать событие `precheck.failed` |
 18| | Документатор недоступен (ошибка сети, таймаут, сервис не работает) | `unavailable` | Блокировать переход; сгенерировать событие `precheck.unavailable` (см. Режим переопределения ниже) |
 19| | Реестр аудита Докуматора отсутствует/поврежден/недоступен для чтения | `fail` | Блокировать переход (отказ в закрытом режиме согласно C-03) |
 20| 
 21| ### Documenter Unavailable — Override Mode
 22| 
 23| Когда Документатор недоступен (вердикт `unavailable`), Модератор MVP НЕ ДОЛЖЕН блокировать операцию на неопределённый срок. Аутентифицированный вызов `council.override_precheck(reason, operator_id)` может быть выполнен, несмотря на сбой:
 24| 
 25| - Переопределение записывает `reason` (свободный текст, объясняющий, почему шлюз был обойден).
 26| - Переопределение записывается в манифест через поле `pre_check_override`.
 27| - Событие `precheck.overridden` синхронно генерируется во время вызова переопределения.
 28| - Переопределение позволяет ровно один последующий переход фазы без нового аудита. После этого перехода следующий рубеж требует еще одной проверки или нового переопределения.
 29| - Переопределение никогда не обходит наличие Роль-ядра, правила Консенсуса или целостности шлюзов Эскалации.
```
