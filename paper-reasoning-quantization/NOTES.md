## Инцидент 2026-11-11: rate-limit 429 + баги раннера

**Что случилось:**
1. **Баги run_cloud.sh:** (а) `MODEL` не экспортировался в `CLOUD_MODEL` → все облачные

3. **Порча данных:** в C1 16/21, в K0 21/21 прогонов содержат `[retry]/[FAIL]` — данные

**Исправления:**

- `queue.sh`: строго последовательная очередь (один облачный поток за раз, затем локальная

- Валидные данные на момент инцидента: C5 (NVFP4 off) — 21/21; C6 (NVFP4 on) — 3/21;
  C1 — 5/21; K0 — 0/21.

**Уроки для плана:** D8 (время) должен учитывать rate-limit-паузы; в §6.3 добавить правило

## Планирование под rate limits neuraldeep (2026-11-11, тариф coder)

**Лимиты ключа (GET /v1/limits):** session **1200 запросов / 3 ч** (окна сброса 09:00/12:00/15:00… UTC),
week **6000 / ISO-неделя** (сброс пн 00:00 UTC), **RPM 60**, параллельность 1 поток.
Ранее полученный бан был по окну `abuse`: клиент повторял запрос после 429 без паузы.

**Проект.cloud_paced.sh (исполняемый планировщик):**
- один поток, concurrency 1; между прогонами пауза ≥3 с;
- gate перед каждым прогоном: `decision.can_request`, cooldown, RPM-остаток **<20 → hold**
  (33% запас от 60), session/ week reserve **≥15%** → иначе ожидание сброса окна;
- **адаптивный пейсинг:** после прогона считает фактический расход (session.used delta) и
  досыпает до устойчивых **≤40 RPM** (2/3 потолка);
- `MAX_RETRIES=1` (без шторма повторов), при `[retry]/429` — пауза 60 с и один повторный
  прогон, затем остановка потока;
- `[FAIL]` больше не считается деградацией (это метрика качества, а не сбой).

**Расписание облачной части:** C1 (21) → K0 (21) → C2 (21), последовательно.
Расход: ~7–10 запросов/прогон (noreason), ~15–20 (thinking) ⇒ **~600 запросов на всё**,
т.е. ≤50% одного 3-часового окна. Оценка времени: C1+K0 ≈ 5–7 мин, C2 ≈ 2–3 ч.
Локальные FP8-прогоны (C3/C4) идут параллельно — другой провайдер, GPU занят только ими.

**Наблюдаемые данные:** за первый прогон C1 (S2, 9 блоков) расход ~9 запросов/12 с;
после включения пейсинга устойчивый темп 26–37 RPM, пики в rolling-минуте до 47–58
(поэтому порог hold поднят с 5 до 20 остатка).

### Находка: утечка reasoning в content у облачного thinking-условия

`qwen3.6-35b-a3b` (reasoning-вариант) в облаке отдаёт цепочку рассуждений **в том же поле
content**, без отдельного канала. В выводе — английские «Let's…», «Wait…», «I need to…»,
«Actually…»: **52.8 строки на прогон** (5…138 из 931). Метрики: D6_echo 1.71 (везде 0),
D1_linecount_fb 4.38 (блок раздувается → построчный fallback, +7–9 запросов на фикстуру),
fuzz-fix 1.67, code_missing 2.71, время 364 c.

Локальные thinking-условия (C4/C6, `enable_thinking:true` через chat_template_kwargs) такого не
дают — trace уходит в отдельное поле. Значит это свойство конкретного облачного эндпоинта, а не
режима thinking как такового.

Решение по C2 (в статье): **принято — trace вырезается пост-обработкой, судейство идёт по
очищенному варианту** (см. P-001b); raw-метрики C2 остаются в таблицах как характеристика
дефекта «как есть».

## Ускорение C2 (2026-11-11, 16:22) — параллельные воркеры

Провайдер отдаёт в `GET /v1/limits` поле **`parallel_limit: 16`** (одновременных chat-запросов)
и `daily_capacity.pct_used: 2.6`. Наш облачный раннер был строго однопоточным, поэтому C2
(9 прогонов × ~6 мин) упирался не в квоту, а в латентность thinking.

Сделан `cloud_worker.sh` — воркер для **непересекающегося** набора фикстур: свой progress-файл,
lock-каталог на фикстуру (не даёт двум воркерам взять одну фикстуру), тот же gate
(RPM ≥20, session/week reserve 15 %, `abuse_cooldown`), тот же `MAX_RETRIES=1` + пауза 60 с.
Строка журнала помечается `concurrency=3 worker=wN`.

Запущено: serial-цепочка добивает S4 rep3 → S5 ×3, воркер w1 — S6 ×3, воркер w2 — S7 ×3.
Итого 3 одновременных запроса против лимита 16 (<20 %), RPM ~3–5 из 60, расход ~1 запрос/1.5 мин
на поток. Критический путь сокращается с ~70 до ~30 мин.

**Методологическая оговорка:** внутри C2 фикстуры S1–S5 сняты при concurrency=1, S6/S7 — при 3.
Влияние батчинга на сэмплинг при temp 0.2 не проверялось; фиксируется как ограничение условия,
между условиями (C1/C2/K0) сравнение идёт по одинаковым фикстурам.

## P-001a, 2026-11-11 — устранение конфаунда D5 (code-span exclusion)

D5/D7 считались по всему тексту, включая инлайн-code. Для структурных фикстур (S4/S5) почти
все «термины глоссария» встречаются только внутри бэктиков как contract-токены (`Session`,
`Subject`, `Consensus`…), поэтому переведённый enum засчитывался как попадание в глоссарий,
а thinking выглядел «точнее по терминологии».

В `metrics/defects.py` добавлены варианты **D5_nc / D7_nc** — те же метрики на прозе
(инлайн-code вырезан регуляркой до подсчёта, EN и RU симметрично). В `aggregate.py` —
колонки `term_missing_nc`, `contam_nc`. Старые колонки сохранены для истории.

**Эффект (среднее на прогон, 21):** C5 off 2.29 → **0.81**; C6 on 1.38 → **0.67** (разница
сократилась с 0.91 до 0.14, т.е. «улучшение терминологии» от thinking практически исчезло).
Для S4: C6 3 → 0, C5 7 → 0 — обе конфигурации переводят всю прозу, различаются только
обработкой code-токенов. Вывод: **D5 без nc-варианта в статье не использовать.**

## P-001b, 2026-11-12 — пост-обработка leakage C2 (`strip_trace.py`)

**Решение оператора:** trace вырезается пост-обработкой, судейство запускается по очищенному
варианту. Обоснование: leakage — свойство эндпоинта, а не режима thinking; без очистки C2
несравним с C4/C6, где trace уходит в отдельный канал.

**Метод** (`metrics/strip_trace.py`, детерминированный, без LLM). Построчно, вне ``` -блоков,
после маскирования инлайн-code, URL и кавычек:
- R1 `marker` — маркеры планирования/мета («Let's…», «Wait», «Final:», «Check terms», ✅);
- R2 `english` / `english-skeleton` — строки с ≥4 латинскими словами, где кириллица <35 %
  букв (в том числе после удаления кавычек — «скелет» строки-рассуждения);
- R3 `mapping` — стрелочные пары терминов с латинской левой частью;
- R4 `stub` / R5 `mapping-quoted` — короткие self-check-заглушки и кавычковые пары;
- R6 `quoted-candidate` — строка целиком является кавычковым кандидатом перевода;
- R7 `junk` — строки без слов;
- R8 `inline-cut` — обрезка хвоста-рассуждения, приклеенного к переводу в одной строке;
- R9 `en-copy` — строки, дословно совпадающие с EN-фикстурой (метаданные/код), не трогаются;
- **R10 `unwrap`** — обратное «разворачивание» полезной нагрузки: у строк вида
  `Final: | \`фаза_id\` | integer | yes | ... |`, `Translation: "..."`, `I'll output: \`...\``
  полезная нагрузка (то, что содержит кириллицу) сохраняется как строка документа. Это важно:
  при утечке единственный перевод табличной строки часто существует **только** внутри такой
  строки-рассуждения; удаление её целиком теряло контент. Заодно разворачиваются
  «забэктикованные» черновые строки таблиц;
- дедуп: из повторов длинной строки остаётся последняя (финальный вариант), при равенстве —
  та, где больше code-спанов.

**Валидация (обязательное условие симметричности):** на C1, K0, C3, C4, C5, C6 (126 прогонов)
фильтр **побайтово не меняет файлы**: удалено 0 строк, `unwrap` не срабатывает, дедуп
не активен (проверка `cmp` по всем 126 файлам — 0 отличий). На C2 удалено **6041 строка**
(288/прогон), развёрнуто **345** полезных нагрузок; по правилам: `marker` 3685, `english` 1307,
`mapping` 429, `stub` 242, `mapping-quoted` 208, `english-skeleton` 91, `quoted-candidate` 73,
`junk` 5, `inline-cut` 1; кириллических среди удалённых — 1179 (19 %). Остаточных маркеров
«Let's/Wait/I'll» — **10 на весь C2** (в основном внутри развёрнутых строк с комментарием).

**Эффект на метрики C2 (среднее на прогон, 21):**

| Метрика | C2 raw | C2 clean | Комментарий |
|---|---|---|---|
| D6_echo | 1.71 | 0.05 | утечка снята |
| D7_nc contaminants | 1.67 | 0.71 | |
| D5_nc term_missing | 0.33 | 0.57 | |
| D3 code_missing | 2.71 | 3.48 | raw-дубликаты **завышали** сохранность токенов |
| D4 num_lost | 0.24 | 0.76 | то же |
| D1_linecount_fb, D2_* | 4.38 / без изм. | без изм. | счётчики stderr, пост-обработка их не меняет |

D3/D4-парадокс объясняется дублированием: в raw один и тот же code-токен встречался в
нескольких черновиках, и метрика «токен присутствует» срабатывала, даже если в финальном
тексте его нет. Остальные встречались **только** в вырезанных строках-рассуждениях.
То есть 3.48 — честная оценка финального текста, а 2.71 — артефакт утечки (дубликаты черновиков
и цитаты токенов внутри рассуждений).

**Ограничения метода:** (1) очистка невосстановима — если модель так и не выдала фрагмент
в финальном тексте, он потерян; (2) дедуп сохраняет последний/наиболее насыщенный code-спанами
вариант, поэтому возможны остаточные русские черновики — длина очищенного C2 составляет
1.59–2.44× от C1 (среднее 2.12: развёрнутые финальные ответы + остаточные черновики),
это фиксируется как остаточный шум условия;
(3) фильтр откалиброван по эвристикам, а не по разметке; ложноположительное удаление
русской прозы возможно только в строках с явными маркерами планирования.

**Файлы:** `runs/C2_cloud_bf16_think_on_clean/` (21 `.md` + скопированные `.log`),
`metrics/strip_trace.py` (флаги `--dir/--out-dir/--dedup/--en-dir`), пересчёт —
`metrics/aggregate.py` (для `*_clean` wall-time наследуется из базового условия).


## P-002, 2026-11-12 — судейство MQM absolute (336 оценок)

**Схема.** 8 наборов × 7 фикстур × 3 повтора × 2 судьи: `gpt-oss-120b` (основной) и
`gemma-4-31b` (второй). Prompt (`metrics/judge.py::MQM_SYS`): EN-источник + пары глоссария
(только релевантные фикстуре, `corpus/gloss_pairs/S*.txt`) + русский кандидат; на выходе строгий
JSON дефектов MQM (critical 25 / major 10 / minor 2, score = 100 − Σ, floor 0).
Запуск: `metrics/judge_batch.py` (resume-safe, gate `/v1/limits`, пейсинг, 8 воркеров,
timeout 420 c). Итог: **336/336** валидных оценок; 6 ячеек проваливались по таймауту на
промптах C2 raw (до 8383 строк) и закрыты через `--repair`.

**Важная правка промпта (после пилота):** в первой версии судья штрафовал падежные формы
глоссарных терминов («консенсус» → «консенсуса»), из-за чего C1 получал 96–100 не по делу.
Добавлены правила: словоизменение требуемого эквивалента — не дефект; дефекты — замена леммы,
пропуск, использование там, где термина в EN нет; кавычки дефекта — точная подстрока RU;
дедупликация. После правки C1 = 85.6 (см. таблицу), пилотные 96+ не воспроизвелись.

**Результаты (среднее по 42 оценкам на условие; 95 % bootstrap-CI):**

**Выводы:**
1. **H1 (качество): thinking устойчиво ухудшает MQM** — −26 баллов на обоих квантованных
   серверах, 15–17 поражений из 21 пары, CI не включает 0. Для облака эффект ещё сильнее
   (−56.5), потому что reasoning утекает в content и разрушает структуру.
2. **Квантование: надёжного эффекта нет.** NVFP4 vs FP8 при одинаковом режиме — Δ в пределах
   ±4 с CI, включающим 0, и судьи расходятся по знаку (gemma +13.2, gpt-oss −20.7 при off).
   То есть 4-битный сервер не «хуже» FP8 по судейской оценке, при этом в 18 раз быстрее.
3. **Глоссарий: эффект небольшой, но в ожидаемую сторону** (−8.2 без глоссария, CI почти
   исключает 0, 11 поражений против 8 побед). Совпадает с D5_nc: K0 1.76 против C1 0.57.
4. **Пост-обработка C2 снижает оценку** (raw 52.7 → clean 29.1). Это не парадокс: на 400–8000
   строках утечки судья физически не перечисляет все дефекты (в raw он видит 1.4 critical,
   в clean — 3.3), поэтому raw-оценка **завышена**. Clean — единственная сопоставимая версия;
   вместе с D3/D4 это согласуется: thinking переводит contract-токены (`session_id` →
   `Сессия_id`), и после вырезания рассуждений дефекты становятся видимыми.
5. **Согласие судей умеренное:** mean |Δscore| = 23.5, Pearson r = 0.55, совпадающая оценка
   только в 23 % пар. Итоги в статье давать по `gpt-oss-120b`, второго — как robustness;
   расхождение само по себе результат (судья без эталона шумит сильнее, чем декларирует).

**Ограничения:** (1) MQM-судья не калиброван по людям — абсолютные баллы условны, значимы
только сравнения; (2) clean-C2 содержит остаточные черновики (длина ×2.1 от C1), что занижает
его оценку — указывается явно; (3) glos-pairs судьи алгоритмические (совпадение термина в EN),
для K0 судья всё равно видит требуемые эквиваленты — это и есть измеряемый эффект «без подсказок»;
(4) 6 ячеек потребовали повтора из-за таймаутов на самых больших промптах.
